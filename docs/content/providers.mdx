The `llm` section of `lawbook.yaml` chooses the model that judges
[`standard` rules](/llm-rules). It is optional; these are the defaults:

```yaml
llm:
  provider: bedrock
  model: anthropic.claude-opus-5-5
  concurrency: 4
  maxBytes: 131072
  cache: true
```

| Key           | Meaning                                                                                        |
| ------------- | ---------------------------------------------------------------------------------------------- |
| `provider`    | `bedrock` (default), `anthropic`, `openai`, `claude-code`, or `codex`. The first three call an API with a key; the last two run the CLI of that name, so a subscription can pay. |
| `model`       | The model id in the provider's own naming. Defaults per provider, see below; `openai` and `codex` have no default, so `model` is required. |
| `region`      | Bedrock only. The AWS region; else `AWS_REGION`, else `AWS_DEFAULT_REGION` from the environment. Setting it under another provider is a config error. |
| `baseUrl`     | OpenAI only. The URL of a server that speaks the Chat Completions API, in place of `https://api.openai.com/v1`. Setting it under another provider is a config error. |
| `concurrency` | How many files a `standard` rule sends to the model at once. A whole number, at least `1`; defaults to `4`. Lower it when the provider rate-limits you, raise it when it does not. |
| `cache`       | Whether verdicts are cached on disk and reused for unchanged files. Defaults to `true`; `--no-cache` overrides one run. See [LLM rules](/llm-rules#verdict-cache). |
| `maxBytes`    | The largest file, in bytes, a `standard` rule sends. A whole number, at least `1`; defaults to `131072` (128 KiB). Larger files are listed as skipped and never judged. See [LLM rules](/llm-rules#large-files). |
| `maxRequests` | The most model requests one run may make. A whole number; no limit by default. A run whose plan exceeds it stops with exit code `2` before any request. `--max-requests` overrides it. See [LLM rules](/llm-rules#budget). |

Unknown keys are errors. A problem building the client, such as a missing
Bedrock region, stops the run with exit code `2` and a one-line message
before any report. A provider or credential error on a request is reported
against the file, the rule shows as `ERROR`, and the run still prints its
report before exiting `2`; see
[LLM rules](/llm-rules#provider-errors).

## Amazon Bedrock

The default. One `provider: bedrock` judges with both the Anthropic and the
OpenAI models Bedrock hosts; the model id picks the endpoint, in the region
the config or the environment names.

```yaml
llm:
  provider: bedrock
  model: anthropic.claude-opus-5-5
  region: us-west-2
```

| Model id                                   | Endpoint                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------ |
| `anthropic.<model>`                        | The Bedrock Messages endpoint, `bedrock-mantle.<region>.api.aws/anthropic`, through the Anthropic Bedrock SDK. |
| `openai.<model>`, `us.openai.<model>`, `global.openai.<model>` | Bedrock's OpenAI-compatible Chat Completions endpoint, `bedrock-runtime.<region>.amazonaws.com/openai/v1`, through the OpenAI SDK. |

Any other family, such as `meta.` or `amazon.`, stops the run with exit code
`2` before any request.

The Messages endpoint takes undated ids: `anthropic.claude-haiku-4-5`, not
`anthropic.claude-haiku-4-5-20251001-v1:0`, and not a `us.` or `global.`
inference-profile id. It also knows fewer models than
`aws bedrock list-foundation-models` lists for the account; an id it does not
serve is reported as unknown to the Messages endpoint, with the undated form
to use. The default is `anthropic.claude-opus-5-5`; pick a cheaper model with
`model` when a rule runs over many files.

The newer OpenAI models, such as `gpt-5.5`, run only through an inference
profile, so name them `us.openai.gpt-5.5`; the bare `openai.gpt-5.5` is
refused for lack of on-demand throughput, and lawbook says which id to use
instead. The open-weight `openai.gpt-oss-120b-1:0` and
`openai.gpt-oss-20b-1:0` work with their bare ids.

Credentials, for both families:

- `AWS_BEARER_TOKEN_BEDROCK`, a Bedrock API key, is sent as a bearer token
  when it is set. AWS's `aws-bedrock-token-generator` mints a twelve-hour one
  from the credential chain.
- Otherwise requests are signed with SigV4 from the usual AWS chain:
  environment variables, a shared config profile, SSO, or an instance role.

`OPENAI_API_KEY` plays no part here. Neither Bedrock endpoint accepts
structured output, so on Bedrock the answer comes back as a call to an
`answer` tool whose input is the probability and the reason: forced where the
model allows it, and requested in the system prompt for Claude Opus 5.5,
Sonnet 5.5, and Fable 5.1, which refuse a forced tool choice. Lawbook checks
the tool's input against the same schema as on the other providers, and
ignores any text the model writes beside the call, such as the reasoning the
gpt-oss models put ahead of their answer. The prompt and the verdict cache
are the same as for the other providers.

## Anthropic API

```yaml
llm:
  provider: anthropic
  model: claude-opus-5-5
```

Credentials come from the environment: `ANTHROPIC_API_KEY`, or a profile
created with `ant auth login`. The default model is `claude-opus-5-5`, and ids
have no prefix.

## OpenAI

```yaml
llm:
  provider: openai
  model: gpt-5
```

The key comes from `OPENAI_API_KEY` in the environment; without one, `check`
exits `2` before any request. Lawbook sends the
same prompt as to the other providers through the Chat Completions API with
a JSON schema response format, so `model` must be one that supports
structured outputs. There is no default model; name one.

`baseUrl` points the same client at any server that speaks Chat Completions,
such as a local model server, so a team can judge files without sending them
outside its network:

```yaml
llm:
  provider: openai
  model: llama3.3
  baseUrl: http://localhost:11434/v1
```

The server must support `response_format` with `json_schema`; one that does
not answers with a provider error. When `OPENAI_API_KEY` is unset, such a
server gets a placeholder key, since most expect a bearer token and check
none. OpenAI caches shared prompt prefixes on
its own, and lawbook reports the tokens it served from that cache under
`cacheReadInputTokens`, as it does for the Anthropic providers.

## Claude Code

```yaml
llm:
  provider: claude-code
  model: claude-opus-5-5
```

Judges through the `claude` command on `PATH`, so a Claude Pro, Max, Team,
or Enterprise subscription that Claude Code is signed into pays for the
requests, and no API key is needed. Install
[Claude Code](https://code.claude.com/docs/en/setup), run `claude auth login`
once, and check `claude auth status` reports `claude.ai`. An API key in
`ANTHROPIC_API_KEY`, or a Console login, works too and is billed as API
usage. The default model is `claude-opus-5-5`; `model` takes a full id or an
alias Claude Code knows, such as `sonnet`.

Each request runs `claude -p` once with the standard as its system prompt,
the files on stdin, and the answer shaped by a JSON schema. The run has no
tools, no MCP servers, and no slash commands, saves no session, and starts
in an empty temporary directory, so the checked project's `CLAUDE.md`,
hooks, and `.mcp.json` never load into the judge. Settings and hooks in
`~/.claude` still apply, since the login lives there; `--bare` is not used
because it would skip the login. Starting the CLI costs a second or two per
file, so this provider suits `scope: set` rules and small file sets better
than a rule over a whole tree. Usage counts come from the CLI's result,
including the tokens it read from and wrote to the prompt cache.

Anthropic permits programmatic use of a Claude subscription through the
Agent SDK and `claude -p`, and such use currently draws from the plan's
usage limits; the terms and the accounting are Anthropic's to change, so
check them before relying on this in CI. Copying the CLI's login token into
`ANTHROPIC_AUTH_TOKEN` for the `anthropic` provider is not permitted; use
this provider instead.

## Codex

```yaml
llm:
  provider: codex
  model: gpt-5-codex
```

Judges through the `codex` command on `PATH`, so the ChatGPT subscription
that Codex is signed into pays for the requests. Install the
[Codex CLI](https://developers.openai.com/codex/cli), run `codex login`
once, and name a `model` the account offers; there is no default. An
`OPENAI_API_KEY` the CLI is configured to use works too, billed as API
usage; OpenAI recommends a key over a subscription login for CI.

Each request runs `codex exec` once in an empty temporary directory with
the standard and the files in one prompt, a read-only sandbox, nothing
persisted, and the answer shaped by a JSON schema through
`--output-schema`. The checked project's `AGENTS.md` never loads into the
judge. Usage counts come from the run's events; Codex counts cached tokens
inside its input count, and lawbook reports them apart as
`cacheReadInputTokens`, as for the other providers. A recent Codex CLI is
needed for `--output-schema` and `--ephemeral`.

## No network in tests

All five providers sit behind one `Judge` interface, and `run` accepts the
factories that build them, so a test or an embedding program can pass its own
judge and never reach a network. The package exports `messagesJudge`, the
provider-neutral core the Anthropic adapter wraps, and `chatJudge`, which the
OpenAI adapter wraps, for anyone adding a provider that speaks the Anthropic
Messages API or the Chat Completions API; `messagesToolJudge` and
`chatToolJudge` are their tool-call twins, which the Bedrock adapter wraps,
for an endpoint that refuses structured output. The CLI
adapters, `claudeCodeJudge` and `codexJudge`, take an `Exec` function that
spawns the command, so a test passes a fake and no CLI runs.
